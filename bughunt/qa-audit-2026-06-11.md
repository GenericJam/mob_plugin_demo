## Suspicious edits (ranked)

### S1 (med-high, VERIFIED) — notification dispatch can crash the screen on a malformed handler entry
`mob/lib/mob/plugins.ex:231-232`: `handler.handler` raises KeyError if the runtime-manifest
entry lacks `:handler`; `invoke_handler/3`'s head requires a 3-tuple, and its internal
`rescue` cannot catch its own FunctionClauseError. Either propagates into `Mob.Screen.handle_info`
→ screen crash. Violates the arc's own iter-1 principle (malformed manifest must not crash
runtime; cf. the settings-schema guard). Reachability low (manifest is generated+validated)
but `read_path/1` accepts arbitrary evaluated terms, so a stale/hand-edited manifest triggers it.
Fix: shape-check before invoke (case on `Map.fetch(handler, :handler)` + non-tuple fallback
clause with Logger.error), + regression test.

### S2 (medium) — `resolve_image/1` returns a RELATIVE path before boot caches the asset root
`mob/lib/mob/plugins.ex` resolve_image: `:persistent_term.get(@pt_asset_root, "")` → with
boot(nil)/pre-boot, returns "assets/plugin/..." while the contract (and native Image loader)
expects absolute. Fix: cache nil, return :error + Logger when uninitialized, + test.

### S3 (medium, KNOWN GAP made concrete) — screencast needs a hand-added AndroidManifest `<service>`
Plugin manifests can't contribute AndroidManifest fragments; the demo hand-added the
mediaProjection foreground service (11efa87). Any next host app activating mob_screencast
builds clean, boots clean, then throws SecurityException at first capture. Same class of gap
as camera's FileProvider/uses-feature. Fix for Hex gate: validator/doctor WARNING when an
activated plugin's manifest declares `android.manifest_fragments_required` (new key), or at
minimum a loud note in MOB_PLUGINS.md + plugin README.

### S4 (medium) — version-skew landmines for apps generated before the plugin build options
Apps generated by older mob_new lack `plugin_zig_nifs`/`plugin_jni_sources`/objc-routing in
build.zig; upgrading mob_dev + activating a plugin fails with "unknown -D option" (Android)
or zig-clang framework-module errors (iOS objc NIFs). Fix: `mix mob.doctor` check that the
app's build.zig declares the plugin options mob_dev emits (mirror of mob_new's drift-guard,
but pointed at the USER's app).

### S5 (low-med) — stale driver_tab still only DETECTED, not enforced
Known gotcha: activating a NIF plugin with a stale checked-in driver_tab → runtime
`:nif_not_loaded`. `mix mob.doctor` / `--check` detect; the native build neither auto-regens
nor hard-fails. (The runtime manifest got the auto-regen treatment in b7bcbdd; driver_tab
should match.) Flagged pre-Hex.

### S6 (low) — runtime-manifest `nifs` list is not platform-filtered
An iOS-only NIF module would be `Code.ensure_loaded` on Android too. NOT a crash today:
the .erl stub beam is platform-agnostic and `load_nif` failure is tolerated by on_load,
and all current plugins are cross-platform. Structural note → document, or filter at
manifest-read using the platform.

### S7 (housekeeping) — demo working tree uncommitted
The Apple-clang objc routing fix in demo ios/build.zig + build_device.zig (verified in sync
with the committed mob_new template), MobPluginBootstrap.kt camera+screencast registration,
regenerated driver_tabs + mob_plugins.exs, mix.exs screencast dep — all correct, none
committed. Commit as one "activate camera+screencast on iOS" change.

Claims investigated and CLEARED (no action): core does load plugin NIFs at boot (e66eccb,
device-verified); missing `nifs` key is defended (`Map.get(..., [])` + `Map.merge(@empty, ...)`);
ensure_nif_modules_loaded idempotent; always-regen hook safe with empty plugin list;
g_preview_session weak-extern semantics correct for the static-link model; driver_tabs
consistent with the activated set; MobPluginBootstrap pattern consistent; iOS/Android
build.zig divergences intentional.
